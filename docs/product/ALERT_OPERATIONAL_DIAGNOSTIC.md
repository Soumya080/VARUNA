## Summary — what already works vs. what is isolated

**Already real and correct, reusable as-is:** materiality gating, severity derivation (deliberately incomplete), dedup, role routing table, `AlertView`/`OperatorCase.alerts` read contract, the mission FSM, and — importantly — the mission authorization enforcement path (JWT principal, `authorize()`-before-mutate, forged-approver rejection, system-principal denial). STEP 6 does **not** need to rebuild mission authorization; it needs to (a) fix the audit-discard bug so that already-correct enforcement becomes *auditable*, and (b) build the layer that does not exist yet.

**Genuinely missing, smallest legitimate set to add:**
1. An `Alert` entity with identity and a lifecycle (`CREATED→ACKNOWLEDGED→ESCALATED→RESOLVED`), persisted per case — built as a thin wrapper correlating existing `DeliveryResult`s, not a second alert-generation pipeline.
2. Fix `MissionService`'s per-request audit-log discard (#12) so mission approvals/denials are actually retrievable.
3. PRAMAN registration of alert lifecycle transitions and mission authorization decisions, so both are answerable from the case's evidence trail.
4. RBAC permissions for acknowledge/escalate/resolve, reusing `varuna_infra.rbac`/`authorize()` exactly as missions already do.
5. API routes: list case alerts, get alert, acknowledge/escalate/resolve.
6. Frontend: real Alert Center (`/alerts`) and Mission Control (`/missions`) pages wired to the API, replacing the two fully-mocked pages, without redesigning their layout.

This is the plan for Phases 1–19 that follows.
